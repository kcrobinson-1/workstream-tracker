# Vision: Work-Streams Tool — Outline

This document is the outline for vision v0 of a session-aware project visualization tool. Each section's summary below describes what the corresponding section of the full vision doc will contain. Working mocks accompany the prose in sections that benefit from them (Sections 3, 4, and possibly 5) so the reader can validate the doc against their mental model; polishing the mocks is deferred to a later revision.

## Summary

This vision describes a session-aware project visualization tool for a single contributor managing 2–5 concurrent Claude Code sessions across separate git worktrees of one repo. The tool's value sits in the layer between humans and live agent work: registering sessions as they start, attaching them to specific stages of specific plan-tree nodes, surfacing live status across the forest of in-flight work, and nudging the contributor to author intent before scoping when it's missing. The tool reads the repo as canonical — the plan tree, the Status tokens, the intent docs — and combines that with a registry of live work-instances reported by sessions through an open API. It is deliberately not a project-management tool: the in-repo planning discipline stays canonical, and the tool's design energy goes into the agent-coupling surface that conventional PM tools don't touch — session-to-node binding, pre-plan-tree triage, inter-actor lineage. v0 is one-way (sessions push, tool listens, no bidirectional talk-back) and present-state-only (no time-series history; closed entities persist as records).

## Outline

### 1. Purpose

The opening section names the problem: a single contributor running 2–5 concurrent Claude Code sessions in separate worktrees loses track of session-to-work mapping (auto-generated worktree names like `quirky-khayyam-fc90c0` don't say what's in them), lineage between parent sessions and spawned side investigations, current state of each session at a glance, and the threads of half-finished investigations dropped during context switches. Current workarounds — a markdown index, bash scripts combining `git worktree list` with `gh pr list`, terminal multiplexers, mental modeling — are enumerated and shown to be insufficient for their specific reasons. The section concludes with what this tool is and isn't: a session-aware project visualization, not a project-management tool.

### 2. Goals and Non-Goals

Names success criteria explicitly: registered sessions attach to specific (node, sub-stage) pairs and become visible in a live forest view; pre-plan-tree work has a first-class triage holding pen; the visualization sorts active work to the top and compresses the rest; an intent tier sits above the existing plan-tree forest and the tool nudges its authoring. Non-goals: replacing the existing in-repo planning discipline, providing PM-tool features the contributor doesn't need (multi-stakeholder views, mobile capture, calendar/Slack integrations), accommodating multiple contributors or multiple repos in v0, time-series history of state evolution.

### 3. Conceptual Model

Defines the load-bearing primitives. **Actors** are registered things doing work — Claude Code sessions, Cowork chats, scheduled jobs; the kind is metadata, not gating identity — with spawned-by edges between them. **Work-instances** are durable units of attributed work that attach to specific (plan-tree-node, sub-stage) pairs or sit in triage; actor-to-work-instance is many-to-many across time (a work-instance can outlive any individual actor and accumulate contributors over its life). The **plan tree** is a forest with mixed-altitude roots — epics and standalone tasks both sit at root level — nodes carry their own Status, and sub-stages within a node (drafting / planning / implementation / validation) have variable cell counts dictated by the plan: D and P typically one each, I and V counts come from the plan and can update mid-flight. The **intent layer** is a separate in-repo doc-family of proposal-shaped artifacts (backlog items, feature proposals, unresolved bugs, intermediate cases) that graduate downward into plan-tree nodes at varying altitudes — an epic-sized intent graduates to an epic-root, a task-sized one graduates to a standalone-task-root. State vocabularies are named at three layers: node Status (read from the repo using exact-match tokens), sub-stage state (none / active / complete; "skipped" collapses into absence — no cell), work-instance state (active / awaiting-user / awaiting-external / backgrounded / completed / abandoned). Lineage exists at the actor level (spawned-by edges) and either as direct work-instance-to-work-instance edges or as relatedness inferred through shared actorship — the choice between those two is an open question.

### 4. User Experience

Describes the visualization at the conceptual level: a vertically tiered view with intent docs in a strip near the top, then three plan-tree-forest tiers — active roots with live sessions, in-flight roots without active actors, landed-or-abandoned — each tier compressing further than the one above. Active roots expand fully through to the active leaf-level sub-stage cells; non-active branches collapse by default. Actor presence renders as decorations on the sub-stage cells they're currently bound to. The triage zone, where uncategorized work-instances live until they attach to a node, is briefly described; full design is deferred. Working mockup images accompany this section to support reviewer validation against mental model; polishing the mocks is deferred to a later revision.

### 5. Tool Boundaries

Names the directional commitments that bound the tool's role. **One-way:** sessions push state to the tool; the tool does not push state back to sessions. Bidirectional talk-back is parked as a possible future feature when working with agents that support inbound channels. **In-repo as canonical:** the plan tree and the intent docs live in the repo; the tool reads them, doesn't author them. Whether the tool ever writes to the repo for quick-capture-of-intent is an open question. **Eventually consistent:** the view derives from current repo state, kept current via a mechanism design picks. Live-on-refresh, in-memory cache with file-watcher invalidation, periodic re-derive, event-triggered re-derive, or hybrid (hot cache for active work, cold record for archived) are all viable — none are ruled out by anything else settled. **Hierarchy is yours:** v0 hardcodes intent → epic → milestone → task → phase by name; the underlying primitives (node, parent edge, status, actor, work-instance) generalize for other schemas in the future without forcing the abstraction now.

### 6. Alternatives Considered

Documents the framing decisions that bound the tool's identity. This isn't a PM tool — the generic project-management features are well-served by Linear, Notion, GitHub Projects, and others, and the differentiated value sits in agent-coupling that those tools don't do. Moving planning out of the repo into an external tool was considered and rejected for a single contributor with strong in-repo discipline and an agent workflow that benefits from the plan being colocated with the code. Abstracting over multiple users' hierarchies from day one was considered and rejected because schema-agnostic tools tend to never become opinionated enough to be useful — better to commit to one contributor's hierarchy and generalize the primitives underneath. Bidirectional talk-back as a primary feature (the agent-drift-prevention value) was considered and demoted — drift-prevention becomes a byproduct of the authoring-nudge mechanism instead, with explicit talk-back staying in the possible-future bucket.

### 7. Open Questions

Names decisions deferred to high-level design or subsequent iterations. The exact authoring-nudge mechanism — empty-space pressure, stale-triage pressure, orphan-pressure, quick-capture cost-reduction, or some combination — is unresolved. The intent tier's exact in-repo doc-type structure (one type vs. several: product proposals, dev backlog, unresolved bugs) is unresolved. Whether the tool ever writes to the repo for quick-capture flow is unresolved. The translation mechanism from plan-doc prose to UX data (strict structured fields, LLM extraction, hybrid) is unresolved. The auto-attach heuristic for placing newly-registered sessions onto plan-tree nodes is unresolved; v0 can assume manual triage. Caching strategy specifics are unresolved. Whether work-instances carry direct digression-edges or rely on shared-actor inference is unresolved. The pre-planning cell-count question (render placeholder cells or render only what the plan has committed to) is unresolved.

### 8. Out of Scope for v0

Names what v0 explicitly doesn't include. Bidirectional agent talk-back and constraint injection. Time-series history of state evolution. Multi-stakeholder support and non-contributor accessibility. Cross-repo aggregation. Multiple contributors. Adaptive hierarchies for other users' mental models. Mobile capture surfaces. Drag-and-drop reorder of root boxes. These are explicit boundary statements, not promises of future work — they're called out so v0 design scope stays small.

### 9. Risks

Distinguishes feasibility risks from feature-shaped risks. **Feasibility risks: none load-bearing.** The technical components are conventional — filesystem walk, exact-token grep, GitHub API, a small registration API, a modest amount of plan-doc parsing for fuzzy fields. No exotic infrastructure required; no AI-dependency the design can't escape from; no scale problems for a single-contributor side project. **Feature risks** are real. The authoring-nudge mechanism may not exert enough pull to actually drive intent-doc authoring, in which case the upstream drift-prevention byproduct doesn't materialize. Session-registration for Cowork-style sessions depends on user discipline since the agent may not invoke registration automatically — uneven invocation is how the visibility goal silently breaks. The triage bucket may accumulate stale uncategorized work-instances if the user doesn't tend to them, becoming clutter rather than a useful surface. Each risk gets a mitigation direction noted, not a mitigation contract.
