# Code Documentation Standard

In-code documentation discipline. The first layer of
documentation is types and names; comments come in where the
contract, intent, or failure behavior is not obvious from the
implementation.

## First layer: types, names, small modules

Use types, clear names, and small modules as the first layer
of documentation. A function whose name and types tell the
reader what it does does not need a docstring explaining what
it does — the docstring just duplicates the signature.

Add inline comments or docstrings only where the code's
contract, intent, or failure behavior is not obvious from the
implementation. The bar is "would a reader who hasn't seen
this code need this comment to understand it?" — not "could a
comment be added?"

## Required comment targets

Comment where the contract is non-obvious. Specifically:

- **File-level responsibility headers** for boundary modules
  (route-level, orchestration, persistence-layer, trust-
  boundary, public-API entry points) whose ownership is not
  obvious from the filename alone.
- **Exported functions, hooks, types, and constants** at
  shared-domain boundaries where the boundary itself is
  load-bearing.
- **Trust, persistence, authorization, and other boundary
  surfaces** where the comment carries the invariant that
  the runtime depends on.
- **API clients and helper functions** whose callers need to
  understand fallback behavior, trusted-versus-untrusted
  input handling, or expected failure modes.
- **Surprising internal behavior** — best-effort observability
  writes, retry semantics, optional fallback modes, fixture
  assumptions, redirect or routing-layer assumptions.
- **Durable persistence-layer logic** (SQL functions,
  triggers, migrations) when the database enforces a
  non-obvious invariant.

The kernel is "comment where the contract is non-obvious."
The specific list above is illustrative; the consuming repo
may extend it with project-specific surfaces (a particular
framework boundary, a particular cross-language interface).

## File-level headers

File-level headers should answer:

- "What is this file responsible for?"
- When useful, "what does this file deliberately not own?"

The second question matters as much as the first: a route-
level component that owns layout and orchestration but not
persistence is more useful to the next reader than one that
just claims to "render the page."

## Avoid comment noise

- Do not add file headers to tiny modules, obvious leaf
  components, or files where the name and exports already
  make ownership clear.
- Do not add comments that merely restate names, types, or
  straightforward control flow.
- Do not use inline comments as phase tracking, release
  status, or TODO storage. Durable follow-up work belongs in
  the repo's designated tracking surface, not in a comment.
- Keep comments short and update them in the same change as
  the behavior they describe.

The phase-tracking-in-comments anti-pattern overlaps with the
doc-currency discipline — comments are durable docs too. See
[`../doc-currency/currency.md`](../doc-currency/currency.md).
