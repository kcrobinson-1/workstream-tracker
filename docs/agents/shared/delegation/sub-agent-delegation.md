# Sub-Agent Delegation

Discipline for delegating work to sub-agents: what sub-agents
inherit (only what's in their prompt), when delegation is narrow
vs. broader, where workflow gates belong, and the orchestrator's
responsibility to catch scope drift.

## Sub-agents inherit only what is in their prompt

Sub-agents spawned via delegation tools do not inherit the
orchestrator's loaded rule set. They only know what is explicitly
included in their prompt. "Follow the project's agent rules" is
not a valid instruction to a sub-agent — the sub-agent cannot read
those rules unless they are pasted in.

This is independent of any specific delegation framework; the
principle applies wherever one agent invokes another with a
bounded prompt.

## Two modes of delegation

When delegating to a sub-agent, choose one of two approaches and
apply it strictly:

**Narrow scope — process rules don't apply.**
Keep the sub-agent's task purely mechanical and self-contained:
reading files, searching the codebase, running a specific named
command, or implementing a single isolated pure function. If the
task is scoped tightly enough that the process rules in this
library would not apply to a human doing the same work, no
additional guidance is needed.

**Broader scope — include the relevant rules directly.**
If the sub-agent will edit files, run validation, or make
structural decisions, include the applicable rules from the
relevant modules verbatim in the prompt. Copy the specific
sections that govern the work being delegated. Do not paraphrase
or summarize down to a one-liner: the sub-agent will execute on
the prompt it sees.

## Workflow gates stay in the orchestrator

Workflow gates belong in the orchestrating session, not in
sub-agents. The change-landing actions — branch creation,
committing, pushing, opening or updating the review surface, doc
currency confirmation, self-review — are high-risk steps that
require the full process context. Keep these in the main session
and delegate only the implementation or research slice that feeds
into them.

The "change-landing actions" framing is intentional: PR creation
is one shape (GitHub-flavored), but the same gate-discipline
applies to every change-landing surface a consuming repo uses.

## Orchestrator catches scope drift

If a delegated task grew beyond its original scope during
execution, the orchestrating session is responsible for catching
the drift and applying the missing gates before treating the work
as done. A sub-agent that returns with a wider diff than its
prompt asked for has produced material that still has to clear
the orchestrator's process gates — it has not produced finished
work.

The orchestrator's responsibility is asymmetric: a narrow-scope
delegation that stayed narrow is finished work; a delegation that
widened during execution needs the orchestrator to run the gates
the sub-agent never had.
