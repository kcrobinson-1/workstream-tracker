# Scope Guardrails and Stop-And-Report

Scope guardrails, named-target-as-boundary discipline,
behavior-preserving discipline, and the stop-and-report conditions
that interrupt a session before it expands past the requested change.

## Treat broad requests as a queue, not a license

Treat broad checklist, cleanup, or refactor requests as a queue of
reviewable-change-sized tasks, not as permission to work through
everything in one thread.

- Prefer one checklist item, one feature slice, or one tightly
  related file family per branch and handoff.
- Combine multiple items only when they share the same files, the
  same validation surface, and still produce a small reviewable
  diff.
- If a user asks for many checklist items at once, record or
  confirm the sequence, then execute only the first bounded slice
  unless the user explicitly asks only for planning.
- If the work grows beyond one cohesive reviewable change, stop
  after updating the checklist or plan with smaller follow-up
  tasks. "Cohesive reviewable change" is the unit the consuming
  repo's review surface treats as one — a PR in GitHub-flavored
  workflows, a CL in others.
- Stop and report instead of expanding scope when the task starts
  requiring behavior changes, unrelated production edits, mixed
  backend/frontend/UI work, or validation outside the originally
  relevant surface.
- Prefer a fresh thread or fresh branch for the next checklist item
  when the previous slice has been committed and handed off.

## Treat the named target as the active boundary

When a prompt identifies a specific checklist item, issue, file
family, feature slice, or validation command, treat that as the
active boundary. Do not work on adjacent cleanup, nearby checklist
items, opportunistic dependency upgrades, or unrelated docs unless
they are necessary to keep the requested change correct and
validated.

## Keep behavior-preserving tasks behavior-preserving

If the requested task is behavior-preserving, keep it
behavior-preserving. Stop and report instead of proceeding if the
implementation appears to require changing product behavior, public
contracts, persistence semantics, authorization rules, routing,
generated artifacts, or unrelated production code.

A behavior-preserving task that "needs" a behavior change to land is
either mis-scoped or surfacing a deeper issue. Either way the right
move is to stop and report, not to widen scope silently.

## Stop-And-Report Conditions

Stop and report instead of continuing when any of these happen.
The list is grouped to make it usable as a checklist, not a
free-form scan:

**Scope.**
- The requested bounded task starts expanding into unrelated
  frontend, backend, database, workflow, dependency, or
  documentation changes.
- The task becomes larger than one cohesive reviewable change.
- The target shape cannot be met without a broader design
  decision.

**Contract.**
- A behavior-preserving task appears to require behavior changes.
- The change would alter public API contracts, status codes,
  response bodies, persistent-store schema or semantics,
  authentication or authorization rules, routing, or production
  platform configuration outside the stated scope.

**Quality.**
- Preserving coverage would require deleting or weakening
  assertions instead of moving, updating, or adding equivalent
  coverage.
- The requested change appears needless, mostly cosmetic, or
  likely to introduce more noise than value after reviewing the
  current code and docs.

**Surface state.**
- The worktree has unrelated uncommitted changes that could be
  mixed into the task (see also `pre-edit-gate.md`).
- Required baseline validation fails before edits (see also
  `pre-edit-gate.md`).

## When you stop, leave the surface readable

When stopping, leave the worktree clean when practical. If stopping
after partial edits, clearly identify the touched files, what
remains incomplete, and whether any validation was run. The handoff
is the artifact the next session will read; sparse or vague handoffs
turn into rework.
