# Change Boundaries

Targeted-fix-over-speculative-refactor discipline. Generalized
statement of "favor maintainable incremental progress."

## Prefer targeted fixes over speculative refactors

Prefer targeted fixes over speculative refactors. Do not introduce
new frameworks, new backend services, or broad architecture
rewrites unless the task clearly calls for that.

The trap this rule blocks: an agent landing on a real bug, deciding
the surrounding code "ought to be cleaner," and turning a one-file
fix into a multi-file rewrite. The rewrite usually trades a known
small risk for an unknown larger risk and obscures the original fix
in review.

## Favor maintainable incremental progress

Favor clarity, reliability, and maintainable incremental progress
over speculative platform expansion. A change is well-shaped when:

- Each commit leaves the repo working.
- The diff is small enough that a reviewer can hold the whole
  change in their head.
- The new code is the simplest thing that solves the stated
  problem, not the most general thing that might solve adjacent
  problems.

This is not "don't ever refactor." It is "refactor as a separate
declared task, not as a side effect of a feature."

## Shared source-of-truth for cross-surface correctness

Do not casually duplicate business or correctness rules across
frontend and backend, or across services. Duplication creates two
enforcement paths that drift independently; eventually one is wrong
and no one notices until a production incident exposes the gap.

When the codebase has a designated shared module that owns
correctness logic (validation, scoring, authorization evaluation),
changes to that logic land in the shared module, and every consuming
surface continues to use it. The shared module is the source of
truth; reimplementing its logic downstream is how the surfaces start
to drift.

If a change appears to require reimplementing correctness logic
outside the shared source — to work around a build constraint,
optimize a hot path, or expose data the shared module doesn't yet
provide — stop and address the root cause first. Extending the
shared module is almost always the right move.
