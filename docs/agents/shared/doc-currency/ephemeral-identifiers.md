# Ephemeral Identifiers in Durable Docs

Durable docs must not embed ephemeral coordination
identifiers. The rule lives here because the failure mode is a
doc-currency failure: the doc reads as authoritative at write
time and rots silently as the identifiers it cites change
meaning.

## The rule

Durable docs (architecture, README, contributor-workflow docs,
agent-rule fragments, code comments, plan docs, milestone
docs, and any other tracked file the project treats as
long-lived) must not embed PR numbers, commit IDs, or other
ephemeral coordination identifiers.

Those references rot:

- A PR number cited inline becomes meaningless when the PR is
  closed and reopened, when a fork or mirror replaces it, or
  when a contributor reading the doc has no access to chase
  the link.
- "As of commit `abc123`" goes stale on the first rebase or
  squash-merge.
- "See PR #X for context" sends the reader off-platform to
  find what the doc itself should already explain.

## What to use instead in durable docs

- File paths plus line numbers or stable anchors
  (`src/module.py:54`, `docs/decisions/auth.md#token-renewal`).
- Function, module, or decision-doc names (the named entity
  is the citation).
- The rule or contract by name, not by where it shipped.
- Date of resolution (`Resolved 2026-05-04`) when historical
  timing matters.
- A section heading or doc-internal anchor when one
  self-contained doc contains the answer.

## Where ephemeral identifiers are acceptable

- **Scoping docs and transient planning artifacts** that are
  deleted at a known terminal moment — these carry no
  long-term rot risk.
- **Change descriptions (PR bodies, MR descriptions)** — they
  live on the review surface, not in tracked file content.
- **Commit messages** — immutable history; point-in-time
  references are expected.
- **The contributor's local notes** outside the repo.

## Phase Status tables and similar audit-trail rows

Audit-trail rows that record where each phase or work item
landed are a special case: prefer the dated form
(`Landed 2026-05-04`) over the PR-number form (`Landed in
PR #NNN`). The PR number adds nothing the merge date and the
plan-doc link don't already convey, and it ages into noise.
If review traceability is genuinely useful, attach the link in
the change description, not in the durable doc.

Recurring trap: a Phase Status row references "this PR" before
the PR number is known, then the author goes back to fill in
the number, then closes that PR and reopens as a different
number, then has to chase every reference. The simplest fix is
not to write the PR number at all.

## The check

Before opening or updating a change for review, scan the diff
for ephemeral coordination identifiers in tracked durable
files. The check is semantic, not pattern-based:

Distinguish identifiers used as **citations** (PR / issue
numbers, commit hashes, "this PR" placeholders, GitHub or
GitLab links, branch-name references tied to a specific work
cycle, ticket IDs, chat permalinks, and similar) from
identifiers used as **load-bearing data** (UUIDs in fixtures,
hex color codes, ETags, slug values, hashes in test inputs,
content the runtime actually consumes).

Citations in tracked durable docs are boundary violations and
should be rewritten using one of the durable forms above;
load-bearing data is content and stays.

This is an agent-judgment pass, not a deterministic grep.
Greps can flag the obvious citation forms efficiently but they
false-positive on legitimate hex / numeric content and they
miss novel leak shapes — a contributor inventing a new
coordination identifier (a fresh ticket system's ID format, a
different chat platform's permalink) won't match any pre-
defined regex. The semantic walk catches both the obvious
shapes and the unforeseen ones.
