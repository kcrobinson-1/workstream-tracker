# Documentation Currency

The durable-docs-stay-synchronized-with-implementation
discipline. Documentation drift compounds: a stale doc is worse
than a missing one because the reader trusts it.

## Documentation is part of the execution loop

Keep documentation synchronized with the implementation. For
structural or multi-file work, documentation is part of the
execution loop, not a final polish pass.

- Maintain or create a local README or equivalent in the
  relevant area when the change introduces or reorganizes
  module structure.
- Document file responsibilities and intended ownership when
  the structure is non-obvious.
- Update area docs as changes are made so the written
  structure never lags far behind the code.

## Status-oriented sections updated in the same change

When a touched doc contains a status-oriented section (for
example `Current State`, `Current status`, rollout status, or
phase status), update that section in the same change so it
reflects the implemented state.

Status sections are the highest-drift category of doc content
because the same doc serves both as authoring surface (this is
what we're doing) and as truth surface (this is what
shipped). Updating it in the same change closes the loop.

## Per-named-doc update triggers

The recommended pattern is for each canonical durable doc in
the consuming repo to carry an explicit trigger list — "update
this doc when X happens" — that fires as part of the change
that makes X happen. The trigger pattern lives here; the
per-doc list lives per-repo.

This pattern depends on the optional **Doc Ownership Table**
convention (defined in the upstream `shared-agent-rules`
`meta` module; not vendored into this repo):
each canonical doc has a named owner and an explicit
trigger list. Repos that adopt the ownership-table convention
get the full trigger-driven version of this rule; repos that
skip it apply the general "keep docs synchronized" principle
above without the per-doc trigger granularity.

For most consuming repos, the durable docs that warrant
trigger lists include some subset of:

- The root README (setup, capabilities, repo structure
  changes).
- The architecture / system-shape doc (ownership, runtime
  flow, trust boundaries, new modules).
- The contributor-workflow doc (validation commands, tooling
  choices, deployment steps).
- The open-questions surface (resolved questions close;
  newly-discovered questions open).
- Any tracking docs for in-flight work the branch advances
  (mark items complete, add follow-ups).
- File-level / module-level documentation when behavior or
  ownership changes meaningfully.

The consuming repo's own currency overlay names the specific
docs and triggers; this module gives the pattern.

## Doc Currency Is a PR Gate

Before opening or updating a change for review, verify that
every named doc that the branch should have touched actually
reflects the implemented state, not the pre-implementation
state.

Walk through the trigger list above and confirm each relevant
update was made. A change is not ready to open if any named
doc still describes the pre-change state. Doc updates belong
in the same branch as the code, not in a follow-up.

This gate is a sibling of the validation gate in
[`../validation/philosophy.md`](../validation/philosophy.md):
both say a change is done when the supporting artifacts
reflect the new state, not when the code change is done.
