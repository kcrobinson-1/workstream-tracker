# UI Review Workflow

Per-session-type playbook for capturing UI screenshots and
building review screenshot evidence. Layer this on top of the
implementation workflow when the change modifies UX, layout,
interaction flow, or user-facing copy.

## UI Review Runs

If you validate the UI by running the app locally and taking
screenshots:

- Prefer a real browser pass over code-only visual guesses. Use
  browser automation (Playwright or the equivalent the repo
  carries) rather than code-only visual guesses whenever it is
  feasible.
- Use the viewport matching the product's primary target. For
  mobile-first products, a mobile viewport first; for
  desktop-first products, a desktop viewport first. Don't assume
  desktop by default.
- Confirm direct route loading as well as the main click-through
  flow.
- Capture the key states you are reviewing, not just the landing
  page.

## Before/after capture for material UX changes

If a change modifies UX, layout, interaction flow, or user-facing
copy in a meaningful way:

- Capture relevant **before** screenshots before editing when
  browser automation is feasible.
- Capture matching **after** screenshots after the implementation
  is complete.
- Use the same routes, states, viewport, and scroll context for
  the before/after pair whenever practical.
- Include a before/after comparison in the change description,
  not just a prose summary.
- Treat this as part of the expected review flow for UX-facing
  changes, not as an optional polish step.

## Reusable capture flow

Prefer the reusable capture workflow already in the repo over
one-off scripts.

- Keep reusable automation logic in the repo's designated
  capture-script location.
- Extend the canonical script when future verification needs
  new routes, states, or capture scenarios instead of creating
  one-off temp scripts (unless the task is truly experimental).

The capture-script location and command names are repo-specific;
this rule is about the discipline of extending the canonical flow
rather than inventing a parallel one.

## Screenshot artifact handling

Treat screenshot artifacts as temporary analysis output:

- Write screenshots under the repo's designated `tmp/` (or
  equivalent) path.
- Do not commit generated screenshots into the repo.
- Make sure the output path is ignored by the repo's version
  control before finishing.
- Do not let one screenshot run overwrite or mix with another
  accidentally. The default expectation is one timestamped
  subfolder per run; only reuse an existing output directory if
  the task explicitly benefits from overwriting a prior
  capture set.

## Including screenshots in the change description

When a change should show screenshots, do not satisfy that by
committing image artifacts into the repository. Use the
following process instead:

1. Capture the images into the repo's temporary path as
   described above.
2. Upload only the selected images to an external image host so
   the change description can reference them by URL.[^image-host-example]
3. Paste the returned image URLs into the change description
   with normal Markdown image syntax.
4. Keep the local screenshots untracked and temporary; do not
   add them to version control, and do not create tracked
   docs-only image folders just to support the change
   description.

[^image-host-example]: One concrete working example used in the
    source codebase was `catbox.moe`, invoked with a one-line
    `curl -F` upload. Consumers should pick their own image host
    appropriate to their organization's data-handling rules —
    e.g., an internal asset bucket, an existing CDN, or a chosen
    third-party host with terms acceptable to the org.

This keeps the repo aligned with the rule that generated
screenshots live under `tmp/` and are not committed, while still
making before/after comparisons visible in review.

## UI self-review

For UI changes, additionally confirm:

- The flow still feels right at the primary viewport.
- Direct route loading still works.
- The key user states (progress, error, completion, edit modes
  applicable to the surface) still make sense.
- Browser tests still use realistic interactions unless there is
  a documented reason not to.
