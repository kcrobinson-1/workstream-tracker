# Debugging Workflow

Per-session-type playbook for diagnosing a failing validation, CI
run, or local test. Layer this on top of the implementation
workflow when the failure surfaces during a code-touching session.

## Debugging Discipline

When a validation step (CI, a local test, a runtime assertion)
fails, the next action must be informed by the actual error, not
by a hypothesis about what the error might be.

### Read the failure surface first

The agent who guesses without reading the failure surface usually
pushes a speculative fix that misses the cause and now has to be
reverted. Read the failure first.

The "failure surface" is whatever output the validation produced —
a log, a CI comment, a stack trace, a build summary, a test
runner's output. The shape varies per repo; the discipline is
the same.

- If failure output is accessible (local run, attached output,
  pasted excerpt, an automated failure comment, a CI artifact),
  read it before making any change.
- If the failure surface is genuinely missing or its content is
  not readable from the session for any reason, stop after at
  most one speculative attempt and ask the human for the log
  content before continuing. Stacked guess-and-push attempts
  pollute the change history with commits that later need to be
  reverted and waste both agent and human review attention.

### Mark speculative fixes as such

When you do push a fix whose connection to the observed failure
is not directly traceable to a specific line of error output, say
so in the commit body and flag that the commit may need to be
reverted if the real cause turns out to be elsewhere.

### Undo speculative commits after finding the cause

After finding the real cause, undo speculative commits from the
same debugging session instead of leaving them in the tree. A
clean final tree is more valuable than a clean history: a
forward-revert commit that restores the pre-speculation state is
acceptable; a rewritten history via force-push is acceptable only
with explicit human permission.

### Verify baseline parity when local passes but CI fails

When a local test passes but CI fails, verify the local
environment actually exercises the same baseline state CI does.
Baseline-state divergence is a recurring source of green-local /
red-CI: the local run is hitting a different setup than CI, and
the test is passing for the wrong reason.[^baseline-example]

[^baseline-example]: In the source codebase this rule came from,
    two concrete traps were `has_table_privilege(role, table, ...)`
    assertions passing vacuously because the local bare-PostgreSQL
    shell hadn't applied the CI baseline grants, and the same
    function's comma-list privilege string returning `true` if
    *any* privilege was held rather than all. Consumers can replace
    this footnote with their own incident; the principle is
    independent of the specific tooling.
