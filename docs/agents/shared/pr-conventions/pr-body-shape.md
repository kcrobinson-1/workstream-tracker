# PR Body Shape

The section schema every change description (PR body, MR
description, CL message) must use. This module ships the
**schema**, not a verbatim template: the section names and
section-level rules are universal; the validation-command list
and surface-specific phrasing live in the consuming repo.

## The schema

Every change description includes the following sections, in
this order. Fill every section; do not omit, rename, or reorder.

### Summary

A short bullet list of what changed. The header-level summary, not
a detailed change log. The reviewer reads this first; everything
else exists to support claims made here.

### Why This Is Worth Merging

Name the concrete maintainability, correctness, user, or
operational value that outweighs the added diff and review cost.
Changes that cannot answer this should not be opened for review;
see [`../core/pre-edit-gate.md`](../core/pre-edit-gate.md) on the
positive-value check.

### User Behavior

Describe what a user can now do differently or what flow behaves
differently. If this is behavior-preserving, say that explicitly
("Behavior-preserving; no user-visible change").

### Contract and Scope

Call out whether this changes public API contracts, status
codes, response bodies, persistent-store schema or semantics,
authentication or authorization rules, routing, production
platform configuration, or generated artifacts. "No contract
changes" is a valid answer; absence of the section is not.

### Target Shape Evidence

For behavior-preserving refactors or checklist work, describe
the final responsibility split and include concrete evidence
such as before/after size or ownership boundaries. For other
changes, write `N/A`. See
[`../workflows/implementation.md`](../workflows/implementation.md)
"Refactor Completion Proof" for what counts as evidence.

### Documentation

List doc updates the branch made. If none are needed, explain
why. The doc-currency gate fires here — see
[`../doc-currency/currency.md`](../doc-currency/currency.md).

### Estimate Deviations

When implementation diverged from an estimate-shaped section of
the plan that drove this change ("Files intentionally not
touched" ended up touched, "Files to touch — new" missed a
file, intended commit boundaries reshuffled, etc.), name the
deviation, the actual outcome, and why the call was right.

Rule deviations are not handled here — they require a
plan-doc change in the same change per
[`workstream-tracker/spec/planning/task-plan.md`](../../../../spec/planning/task-plan.md)
"Plan-to-PR Completion Gate." Estimate deviations are normal
and reported here; rule deviations are not normal and require
fixing the plan.

Write `N/A` if no estimate deviated, or if this change was not
driven by a plan doc.

### UX Review

For UX, layout, interaction, or user-facing copy changes,
include before/after screenshots or explain why browser
screenshots were not feasible. For non-UX changes, write `N/A`.
See [`../workflows/ui-review.md`](../workflows/ui-review.md) for
the capture flow.

### Validation

List the validation commands you actually ran. Check each off
or annotate clearly. List any named check that could not be
run, and why. See
[`../validation/philosophy.md`](../validation/philosophy.md)
"Validation Honesty" for the discipline behind this section.

The consuming repo's overlay names which specific commands
appear in this section; the schema is the universal contract.

### Remaining Risk

Name residual risk, blockers, or follow-up work. **Never leave
this blank.** Write "None known." if there are no residual
risks. Blank Remaining Risk sections are a tell that the
reviewer should look harder, not that the change is clean.

## Section-specific rules

- **Estimate Deviations.** Plan-implementing changes name
  every estimate deviation; rule deviations require a same-PR
  plan-doc edit per the Completion Gate (see cross-reference
  above). Write `N/A` if no estimate deviated.
- **Validation.** Check off every item you actually ran. Add
  rows for any extra commands run. Explicitly list any named
  check that could not be run and why.
- **Remaining Risk.** Never blank. "None known." is fine when
  true; absence of the section header is not.
