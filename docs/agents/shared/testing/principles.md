# Testing Principles

Test design discipline. Where to put tests, what to mock, what
to leave un-mocked, and how to keep CI deterministic. The
**test boundary** discipline — what makes a test data-coupled
versus contract-coupled — lives in
[`../validation/philosophy.md`](../validation/philosophy.md);
this module cross-references it for the testing-design context.

## Test the seams where bugs would actually hurt

Identify the highest-value seams in the codebase and prioritize
test coverage there. High-value seams are usually:

- The trust boundary (input validation, authorization,
  persistence-layer enforcement).
- Shared correctness logic both frontend and backend rely on.
- Idempotency and uniqueness logic in the persistent store.
- The primary user-facing flow end-to-end.

Coverage outside these seams should earn its keep on its own
merits, not just because it adds a row in the test count.

## Prefer one strong test at the right layer over three weak tests at the wrong layer

A test at the right layer catches real failures of the contract
it verifies. Tests at the wrong layer either pass for the wrong
reason or fail for unrelated reasons. Examples of the
"right-layer" framing:

- Test pure shared logic directly, not only through the UI
  click path.
- Test the persistent-store RPC or stored procedure in a real
  database, not by mocking the database and asserting on call
  arguments.
- Test the primary user-facing flow in a real browser, not by
  building many shallow component snapshots.

The trap this rule blocks: stacking many shallow tests at a
convenient layer to feel covered, when the contract that
actually matters lives one layer down and is untested.

## Mock external boundaries, not core business rules

Use mocks when isolating the unit under test from network
behavior or environment effects. Do not mock:

- The shared correctness/domain logic when *that* is the
  thing being trusted.
- The persistent-store function or query when testing
  entitlement, idempotency, or constraint behavior.
- Internal hooks or selectors with shallow component tests
  that only assert implementation details.

Prefer mocking at the network or environment boundary (`fetch`,
HTTP layer, env-var-driven config) over mocking internal
modules. When mocking is unavoidable for internal modules,
document the reason in the test file.

## Keep CI deterministic

Continuous integration should be reproducible on every run.
Avoid in CI:

- A shared remote backend or service that multiple builds
  contend over.
- Manually managed test data outside the test setup.
- Flaky visual-diff gates.
- Heavyweight setup costs that only some PRs need.

When backend realism is needed, use a locally-started
service-under-test (a local database, a local server) per
build rather than a shared remote instance.[^ci-determinism-example]

[^ci-determinism-example]: One concrete pattern: spin up a
    local containerized backend per CI job. A pattern to
    avoid: relying on a shared remote project that any other
    build can mutate mid-run. Consumers replace this footnote
    with the specific approach their tooling supports.

## Test boundary discipline — see validation philosophy

The test boundary rule — "a unit test should fail when the
unit's contract is violated and pass otherwise; if unrelated
data requires editing the test, the boundary is wrong" — is
load-bearing for testing design but is documented as part of
the validation discipline.

The primary statement is in
[`../validation/philosophy.md`](../validation/philosophy.md)
"Test Boundary Discipline." Implementers writing or
modifying tests should walk every modified test through the
boundary question there before opening a change for review.
