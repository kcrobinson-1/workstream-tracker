# Rule Additions

**Deep meta-rule.** Adding a rule has a cost: every additional
rule increases the cognitive load on every future session that
has to read and apply the rule set. This rule forces the
trade-off to be articulated at addition time rather than
deferred to a future consolidation pass.

## The rule

A change that adds a new rule to a consuming repo's local
agent-rule surface (or to the shared library, via a proposal)
must either:

- **(a)** Name a rule it deletes or merges into the new one, or
- **(b)** State explicitly why no existing rule could be
  retired.

The change description names the trade-off. "We added a rule
and didn't retire anything because the new rule covers a class
of failure no existing rule addressed" is a valid answer; the
absence of any reckoning is not.

## Why this is a deep meta-rule

Rule systems compound: every rule that doesn't get retired
when it should have stays in the read surface, dilutes the
load-bearing rules around it, and gets ignored more easily
because the surface is too dense to skim. The deep meta-rule
exists because the system tends, without intervention, toward
ever-growing rule mass.

The discipline is *forced trade-off articulation*, not "you
can't add rules." Adding rules is fine. Adding rules without
asking whether the existing set still earns its keep is not.

## Carrier surface

The rule says "the change description names the trade-off."
That carrier is intentionally generic:

- In GitHub-flavored workflows, the change description is the
  PR body.
- In other workflows it might be the MR description, the CL
  message, an attached design doc, or a commit-message
  footer.

The discipline is the same wherever the change-landing surface
carries justification text.

## Optional extension: roadmap-fit analysis

Consumers may extend this rule to require a roadmap-fit
analysis when the repo maintains a rule-system roadmap — a
verdict, the concrete delta on rule surface (entries added,
revised, retired), and whether the change moves with or
against the direction named in the roadmap. The shared rule
does not prescribe this: most consuming repos won't maintain
a rule-system roadmap, and requiring the analysis for repos
that don't have one is friction without payoff. Repos that do
maintain a roadmap should require the analysis explicitly in
their local rule-additions overlay.

## What this rule does not say

This rule does not say "rules are immutable" or "no new rules
in less than N months." Rule churn is fine; *unaccounted-for*
rule churn is the failure mode.
