# Light vs Full Thresholds

**Shallow meta-rule.** When a repo has multiple gating layers
— "is this a lightweight change?" at the implementation layer,
"is this a narrow-surface change?" at the planning layer,
"does this need a design doc?" at the architecture layer — the
thresholds for each gate differ, and conflation across layers
is a recurring failure mode.

## The rule

When the repo has multiple gating layers, name each gate's
threshold and call out where the thresholds differ. The
recurring failure mode is reading one gate's threshold as if it
applied to a different gate.

The gate definitions live in their respective modules; the
meta-rule is *naming the layered structure explicitly* so each
gate's threshold is unambiguous from the rule prose that uses
it.

## Canonical illustration: lightweight implementation vs narrow-surface planning

The shipped library carries two gates that share the
"how small does this change need to be to skip a heavier
process?" question but answer it for different work:

- **Lightweight-vs-full implementation path** (in
  [`../workflows/implementation.md`](../workflows/implementation.md))
  — gates whether an *unplanned implementation session* uses
  the 5-step lightweight checklist or the 11-step full
  structured checklist. The threshold there is strict (few
  files, single subsystem, no contract changes, no schema
  changes, local test surface).

- **Narrow-surface plan skipping** (in
  [`workstream-tracker/spec/planning/task-plan.md`](../../../../spec/planning/task-plan.md)
  "Narrow-surface plans may skip the scoping doc") — gates
  whether a *planned task or phase* writes a scoping doc.
  The threshold there governs scoping-artifact necessity, not
  commit/validation discipline.

The conflation trap: an agent reads "narrow surface, no
scoping doc needed" and concludes the implementation path can
also be lightweight. The two gates measure different things.
A change can qualify as narrow-surface for plan-drafting
purposes and still need the full structured implementation
path — the scoping-doc threshold is about whether to write a
scoping artifact, not about commit-or-validation discipline.

The fix is what this meta-rule prescribes: name each
threshold explicitly, in its own module, with cross-references
to the others when the thresholds adjoin.

## Other examples a consuming repo may carry

- "Is this a hotfix?" at the deployment layer vs "is this a
  lightweight implementation?" at the dev layer. The two
  thresholds usually differ.
- "Does this need a design review?" at the architecture layer
  vs "does this need a planning doc?" at the workstream
  layer.

Whenever the consuming repo carries more than one such gate,
the rule applies: name each threshold explicitly.

## How to apply it

When writing a rule that mentions a threshold:

1. Name the gating layer the threshold applies to.
2. If a sibling gating layer carries a related threshold,
   cross-reference it and call out the difference.
3. Avoid generic phrases like "for small changes" — replace
   with the named-threshold from the relevant gate.
