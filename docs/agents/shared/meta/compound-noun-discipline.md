# Compound-Noun Discipline

**Shallow meta-rule.** Rule prose is read across many sessions
by many agents; ambiguous nouns in rule prose cost more than
the same ambiguity in regular code comments. This rule applies
to any rule-bearing surface in the consuming repo and in this
library itself.

## The rule

In rule prose, any noun with both a narrow and a broad meaning
needs explicit disambiguation when ambiguity could arise.

The pattern is: when one word in the consuming repo's
vocabulary names multiple distinct things at different levels
of scope, every rule sentence that uses the word makes the
level explicit. Compound forms (`<modifier>-<noun>`,
`<scope>-<noun>`, hyphenated, or qualified by the surrounding
clause) beat bare nouns whenever a reader could plausibly load
the wrong meaning.

## How to apply it

When writing a new rule:

1. Identify nouns in the rule prose that the repo's vocabulary
   uses for more than one scope.
2. Replace bare uses with the explicit compound (or rephrase
   the sentence so the scope is unambiguous from context).
3. If the disambiguation is needed often enough, define the
   compound terms in a short glossary at the top of the rule
   file or in the consuming repo's vocabulary reference.

## Illustrative examples

The source codebase this rule came from used "plan" and "task"
as overloaded nouns: "plan" could mean an epic-level plan, a
milestone plan, a task plan, or a phase plan; "task" could
mean a checklist item, a planned task at the task-plan level,
or a backlog item. The rule there required compound forms
("task plan," "phase plan," "task-level," "phase-level") over
bare "plan" or bare "task" wherever ambiguity could arise.

Other consuming repos have their own overloaded nouns. Common
candidates that surface in rule prose across many codebases:

- "Event" (domain event vs. UI event vs. analytics event).
- "Session" (agent session vs. user session vs. test session).
- "Job" (CI job vs. background job vs. cron job).
- "Build" (CI build vs. production build vs. local build).
- "Test" (unit test vs. integration test vs. smoke test).

The principle is the same: disambiguate by adding a modifier,
not by hoping context will resolve.

## What this rule does not say

This rule does not say "never use bare nouns." Many sentences
have unambiguous bare-noun uses (when the surrounding clause
makes the scope obvious). The rule fires when ambiguity could
plausibly arise.
