# Validation Philosophy

The universal validation discipline: what counts as a check, how
to be honest about what ran, the continuous-validation cadence,
regression discipline, PR readiness, the test boundary, the
testing-tier discipline, and the no-prod-credentials-on-laptops
rule.

The validation *commands* — `npm run lint`, `pytest`, `cargo
test`, the project-specific scripts — live in the consuming
repo. This module is about the discipline that wraps whatever
commands the repo carries. The split is deliberate: the
philosophy generalizes; the surface does not.

## Validation is a gate, not a final-step polish

Validation is part of the change, not a final-step polish pass.
The cadence and the honesty rules below apply continuously, not
once at handoff.

This is the load-bearing kernel: the "doc currency is a PR
gate" rule and the validation rules here are siblings. Both
say: a change isn't done when the code change is done; it's
done when the supporting artifacts (validation runs, doc
updates) also reflect the new state.

## Validation Expectations

Run the checks relevant to the area you changed. The consuming
repo names which checks fire for which surfaces; this module
defines the discipline around running them.

If you could not run a relevant check, say so explicitly and
explain why. Silently omitting a check from the validation
report is the trap; named-and-explained is fine.

## Validation Honesty

Do not overstate what was validated.

- Run the validation commands named by the task or checklist
  before handoff.
- If you added a new test command, validation surface, or
  workflow step, prefer to run it locally before opening or
  updating a change for review.
- If you added a new top-level validation path, run the
  integrated repo command that is supposed to cover it, not
  just the new subcommand in isolation.
- If a validation command depends on local services or
  runners, exercise it from a clean start when practical, not
  only from a warm reused state.
- If a new validation step cannot be run locally, call out the
  exact blocker in the handoff and change description.
- Do not describe a branch as fully validated if any newly
  introduced check has not been exercised end-to-end.
- If docs describe a test as covering the "real" backend or
  browser path, make sure the implementation actually does
  that. If the test runs in fallback or mocked mode, document
  that precisely.
- If baseline validation failed and the task was stopped
  before edits, report that as a baseline failure, not as a
  failed implementation.

## Continuous Validation

Do not wait until the end of a large change to discover that
the branch drifted.

- For multi-file or non-trivial work, run the relevant checks
  before each commit, not only before handoff.
- When code movement changes test layout, confirm the normal
  repo runners still pick up the affected tests.
- When adding a new test file pattern or directory, make sure
  the configured runner includes it.
- If a step cannot yet pass validation, shrink the step until
  it can.

## PR Readiness

Treat changes opened for review as reviewable engineering
work, not speculative drafts with known unverified edges
hidden inside them.

- Before opening or updating a change for review, confirm
  that all docs the branch should have touched are current —
  see [`../doc-currency/currency.md`](../doc-currency/currency.md)
  "Doc Currency Is a PR Gate."
- Before opening or updating a change for review, make sure
  every new script or validation command added by the branch
  is runnable by a contributor following repo docs.
- If a change is intentionally still exploratory, keep it
  clearly framed as draft work and do not present it as
  merge-ready.
- For new test runners or test directories, confirm the
  existing runners do not accidentally pick them up or
  conflict with them.
- If a helper script depends on local tools, either make the
  script self-checking with clear failure messages or document
  the setup in the same change.
- For new helper scripts that start local services or
  background processes, validate teardown as well as setup so
  CI cannot hang after the assertions already passed.
- Prefer fixing local workflow blockers in the repo when
  reasonable instead of relying on CI to be the first real
  execution environment.

## Regression Discipline

When a change touches testing infrastructure, validation
commands, CI, or local setup, review it for operational
regressions in addition to product regressions.

- Make sure new validation commands do not silently depend on
  undeclared local state.
- Make sure new validation commands work from both
  fresh-start and warm-start local states when that
  distinction matters.
- Make sure browser tests are deterministic about which
  backend path they exercise.
- Make sure helper scripts are safe to rerun and fail with
  actionable guidance.
- Make sure helper scripts emit enough progress logging and
  bounded timeouts to debug CI stalls.
- Make sure CI does not pay heavyweight setup costs earlier
  than necessary.
- Make sure local validation steps do not mutate workspace
  state in ways that break later commands.

## Test Boundary Discipline

A unit test should fail when the unit's contract is violated
and pass otherwise. If unrelated data — a new feature flag, a
new sample fixture, a new config entry, a new domain row —
requires editing the test, the test boundary is wrong: the
test is asserting against data that lives outside its unit's
contract.

Before opening or updating a change that adds or modifies
tests, walk every modified or added test through this
question:

> **"If a contributor added an unrelated entry in this domain
> tomorrow, would this test need editing?"**

If the answer is yes, the test is data-coupled. Refactor
before opening the change. Common fixes:

- **Mock the cross-boundary input.** When the test verifies
  algorithm or matcher behavior, build a synthetic config /
  fixture / input set inside the test rather than reading the
  live artifact. Live-artifact reads belong in
  shape-correctness tests, not in algorithm tests.
- **Parametrize over the source-of-truth constant.** When
  the test legitimately cares about a domain set, iterate
  over the constant rather than hardcoding members. Adding
  to the constant then automatically extends the walk.
- **Assert the load-bearing invariant, not the specific
  population.** When two surfaces must mirror each other,
  assert byte-equivalence between them — that catches real
  drift. Adding to one without updating the other still
  fails the test; adding to an unrelated slot in either
  surface does not.
- **Separate format from algorithm.** Format / shape-
  correctness tests run against the live artifact and assert
  structural rules. Algorithm tests run against synthetic
  inputs and assert behavior. Mixing them couples the test
  to whatever data is in the artifact today.

If the test legitimately needs to enumerate domain data —
e.g., a regression fixture for a specific historical bug —
leave a comment naming what triggers a future edit so the
next contributor sees the trap before tripping it.

Recurring trap: a unit test reads a live config or fixture,
hardcodes the entries present today, and breaks every time
someone adds an unrelated entry. The fix is to assert the
contract that links the source-of-truth constant to the
consuming surface (catches real drift) and to test the
matching algorithm against synthetic inputs.

## Testing Tiers Discipline

Distinguish testing tiers that are valid pre-merge gates from
tiers that are not.

- **Gate merge only on tiers the implementer can actually
  execute against the pre-merge state of the code.** A check
  that can only pass post-deploy (production smoke, post-
  release verification) is not a pre-merge gate. Plans that
  include post-release checks land in two phases: the
  pre-merge gate, then the post-release verification with
  its own status flip. See `workstream-tracker/spec/` for
  the plan-doc-side framing of two-phase gates.
- **Do not require contributors to configure production
  credentials on local laptops.** Production credentials,
  production fixture identities, and production service-role
  keys are owned by the release/ops surface, not by
  individual contributors. A check that implicitly requires
  them on the implementer's laptop is misrouting validation
  — fix the validation surface, not the secret storage.
