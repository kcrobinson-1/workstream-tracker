# Rename-Aware Diff Classification Audit

**Trigger.** A diff includes a rename, move, or large
restructuring that the version control tooling presents as an
add+delete pair rather than a recognized rename — and the change
description claims "no behavior changed" or "pure rename."

**Check.** Before accepting "no behavior changed" claims, walk
each renamed surface against the actual diff content:

1. Pair up each add-side file with its delete-side counterpart.
   Treat the pair as a unit; the tooling's per-file view is
   misleading when classifying behavior.
2. For each pair, diff the content (e.g., `git diff --find-
   renames` or the equivalent), not the per-file add/delete
   patches. Behavior changes hide inside an apparent rename
   when the content actually drifted by a few lines.
3. Confirm that every test, doc reference, import, route
   binding, configuration entry, or other consumer of the
   renamed surface was updated to the new name. Renames that
   leave consumers pointing at the old name look like behavior
   changes (the old name is now broken).
4. Confirm that the responsibility split implied by the new
   name matches the actual content. A rename that promises
   one thing and ships another is misnamed at best, a hidden
   behavior change at worst.

The trap this audit blocks: a "rename" that the tooling shows
as add+delete actually carries small content changes — a default
value flipped, an import order rearranged in a way that changes
side-effect ordering, a comment turned into executable code by
accident. The reviewer scans the add side, sees mostly the same
text, and approves.

**Example (illustrative).** A directory rename that the tool
classified as add+delete also flipped a default boolean
parameter from `true` to `false` in one of the moved files.
The PR description called it "pure rename, no behavior change."
The fix is to add the hand-classification pass to the rename
workflow and to call out the parameter flip in the change
description. Consumers can replace this example.
