# Error Surfacing for User-Initiated Mutations

**Trigger.** A diff adds or modifies a code path where a
user-initiated action causes a write to the persistent store or
to an external system — form submit, button click, drag-and-drop
commit, command invocation — and the write can fail (network
error, validation error, server-side rejection, conflict).

**Check.** For every such write, walk the success/failure
branches and confirm:

1. The failure case surfaces an error to the user. Silent
   failure — the write fails, the UI returns to its idle state,
   and the user assumes success — is the trap.
2. The error message tells the user something actionable, not
   just "an error occurred." Distinguish at least: validation
   error (user can fix), conflict (the state changed under
   them), transient failure (retry is reasonable), and
   unexpected error (report to support).
3. If the action is destructive or non-idempotent, the UI does
   not optimistically claim success until the write has
   actually committed.
4. If the write goes through multiple steps (write +
   reconciliation read, write + audit log, etc.), a failure in
   a *follow-up* step does not mis-classify the original write
   as failed. A best-effort follow-up that fails should not
   surface as the operation failing — unless the contract
   explicitly says the flow is atomic.

**Example (illustrative).** A "Save draft" button calls a
backend write; the write times out at the network layer. The
button's loading state clears, no toast or banner fires, the
form looks idle. The user assumes the draft saved and closes the
tab. The fix is to render a persistent error state when the
write does not confirm. Consumers can replace this example with
an incident from their own codebase.
