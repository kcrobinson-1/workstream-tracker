# Readiness Gate Truthfulness Audit

**Trigger.** A diff adds or modifies a code path that announces
readiness, health, or completion — a health-check endpoint, a
"ready" status emitted by a startup script, a "deploy succeeded"
signal posted to a coordination surface, a `Status: Landed` flag
flipped on a tracked artifact, a "post-merge smoke passed" claim
in a release note.

**Check.** For every readiness signal in the diff, walk the
relationship between the signal and the conditions it claims to
verify:

1. Identify the named conditions the readiness signal is
   supposed to assert. ("Database migration applied,"
   "deployed code serves the new route," "post-release smoke
   suite passed," "all phase checks green.")
2. Confirm the gate actually verifies each named condition
   before announcing readiness — not best-effort, not "the
   thing started so probably it's fine," not a sleep followed
   by an assumption.
3. Confirm that a failing condition causes the readiness
   signal to *not* fire, rather than firing with a warning or
   a degraded-mode flag the consumer is expected to notice.
4. Confirm the readiness signal's documentation, if any,
   matches what it actually checks. A signal that documents
   five conditions but only verifies three is lying by
   omission.

The trap this audit blocks: a readiness gate that says "ready"
on best-effort grounds (the deploy finished without throwing;
the migration command exited zero; the smoke command was
invoked, regardless of whether the assertions inside ran). The
consumer of the gate then treats "ready" as proof of the named
conditions, and a real failure ships silently because nothing
actually checked.

**Example (illustrative).** A plan-doc `Status: Landed` flip is
treated as authoritative proof that post-release smoke passed.
But the smoke workflow that's supposed to flip the status only
checks whether the deployment job exited zero — not whether the
deployed surface answers correctly. A misconfigured environment
deploys "successfully" but the new route returns 500s; the
`Landed` status is set, and the failure is only caught when a
human notices the route is broken. The fix is to make the
readiness gate verify the named post-release smoke assertion
output, not just the deploy exit code. Consumers can replace
this example.
