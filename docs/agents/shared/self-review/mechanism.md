# Self-Review Catalog Mechanism

The catalog mechanism — its purpose, the entry format, the
recurrence-based lifecycle, and the commit-boundary execution
discipline. This is a **deep meta-rule** about how the rule
system organizes recurring-issue knowledge; changes here ripple
across every consumer.

The catalog *content* — the audit entries themselves — lives
elsewhere: seeded universals under `seed-audits/`, and
project-specific audits in the consuming repo's local catalog.

## Purpose

Named, reusable audits to run on a diff before push. Each audit
is a reviewer's lens — a specific class of issue that reviewers
(human or AI) would otherwise flag.

The goal: catch recurring issues at self-review time, not at
review time. Self-review by itself is cheap. Good self-review is
cheap **and** focused: knowing which specific failure modes to
look for, and what concrete checks tell you you're safe.

## Entry format

Every entry has three fields:

- **Trigger.** A one-sentence diff pattern describing what fires
  the audit — not a vibe, not "think about X." A trigger like
  "any migration touches GRANT EXECUTE" is actionable; "think
  about authorization" is not. Short triggers beat elaborate
  ones.
- **Check.** A concrete walk-through the reviewer-or-agent
  performs against the diff. Enumerated steps, not prose.
- **Example.** A concrete instance the audit would have caught.
  Linked to a durable incident, PR, or commit reference when
  one exists; illustrative-and-replaceable when the consuming
  repo has its own war story.

The fields are load-bearing in this order: the Trigger is the
match key the agent runs against the diff surface; the Check is
the audit body; the Example is what makes the rule memorable.

## Lifecycle

Add an audit when **either**:

- A reviewer (human or AI) flags the same class of issue on two
  or more distinct changes, **or**
- A single high-severity finding has a root cause that clearly
  generalizes beyond the specific file.

Drop an audit when:

- An automated check (linter, type system, CI gate) now enforces
  it. The audit is duplicating an automated gate; the gate wins.
- The pattern has not recurred in a long while (six months is a
  reasonable default) and new code in that surface is unlikely
  to reintroduce it.

The recurrence threshold matters: audits added on a single
non-generalizing finding clutter the catalog and reduce the
signal-to-noise of self-review.

## When audits run

Audits run at every commit boundary, not only at the end of the
branch. For multi-commit branches, run the audits at each commit
boundary; small diffs are easier to audit honestly than large
ones.

When a consuming repo carries a plan-doc system, the plan can
name the audits it commits to running up-front — see the
plan-implementation rules in `workstream-tracker/spec/`. The
self-review catalog and the plan-time-named-audits pattern
compose: the plan names which audits apply; the catalog defines
what each audit means.
