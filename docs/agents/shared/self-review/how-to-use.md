# How to Use Self-Review

The general self-review checklist every session runs before
handoff, plus the discipline for walking named catalog audits.

## Step 1 — walk named catalog audits matching the diff surface

Before finishing, walk the audits from the consuming repo's
self-review catalog that match the diff's surfaces. Match on the
**Trigger** field — that's the audit's diff-pattern key.

The consuming repo's catalog lives at a stable per-repo path
(conventionally `docs/agents/local/self-review-catalog.md` or
equivalent). The shared seed audits are imported into that
catalog at adoption time; project-specific audits are added on
top.

When the consuming repo's plan-doc system is in use, the plan
names which audits apply at plan time — implementation just
walks the named list. When there is no plan, match audits to the
diff surface yourself.

## Step 2 — run the general self-review checklist

The four-group split below covers what every change is reviewed
against. Each group is its own load-bearing principle; the
groups are not redundant, and a quick scan that conflates them
misses the categories that catch real bugs.

### Correctness

The diff is correct and complete:

- Correctness of the change itself.
- Regressions in any existing flow the diff touches.
- Readability and maintainability of the new code.
- Duplicated logic introduced by the change.
- Complete call-site coverage: when a function signature
  changes or a new parameter is added, audit every call site
  including error, retry, and fallback paths — not just the
  primary happy path.
- Whether the final change is still positive value for the
  codebase and should be merged, rather than being needless
  churn or noise that offsets its benefit.

### Drift

Supporting artifacts are current:

- Stale inline comments or stale docs — walk the doc-currency
  triggers and confirm every relevant named doc was updated.
  See [`../doc-currency/currency.md`](../doc-currency/currency.md).
- Missing validation — every new test, command, or workflow
  step the branch added is exercised end-to-end before handoff.
- Test alignment with the diff (no test asserting against
  removed structure, no test silently skipped).

### Downstream impact

Consumers of changed code or contracts are accounted for:

- Accessibility or usability regressions in any user-facing
  flow.
- Operational regressions in addition to product regressions
  when the change touches validation, CI, or local setup. See
  [`../validation/philosophy.md`](../validation/philosophy.md)
  "Regression Discipline."
- Trust-boundary effects: for backend or trust-related changes,
  confirm that client input is still validated defensively;
  shared correctness logic remains the source of truth where
  applicable; every new write reachable from a public or
  origin-gated surface has persistence-layer enforcement, not
  just application-layer checks that a future code path could
  skip.

### Scope discipline

The diff stayed inside the requested boundary:

- The final diff stays inside the requested scope.
- The checklist item or prompt can be mapped to concrete
  changed files.
- Any status change is backed by target-shape evidence, not
  only by passing tests.
- The handoff says whether behavior changed; for
  behavior-preserving tasks, the answer should be "no" or
  should explain why the task stopped.
- The handoff lists validation actually run, files changed,
  follow-up tasks added, and any remaining risk or blocker.

## Step 3 — bounded task confirmations

For any bounded checklist or refactor task, also confirm:

- The final diff stays inside the requested scope.
- The checklist item or prompt can be mapped to concrete
  changed files.
- Any status change is backed by target-shape evidence, not
  only by passing tests.
- The handoff says whether behavior changed; for behavior-
  preserving tasks, the answer should be "no" or should
  explain why the task stopped.
- The handoff lists validation actually run, files changed,
  follow-up tasks added, and any remaining risk or blocker.

## Step 4 — backend / trust-boundary additions

For backend or trust-related changes, confirm:

- Client input is still validated defensively at the trust
  boundary.
- Any designated shared source-of-truth logic remains the
  source of truth where applicable.
- Every new write reachable from a public or origin-gated
  surface has persistence-layer enforcement (referential
  integrity, constraints) — not just application-layer checks
  a future code path could skip. See
  [`../core/pre-edit-gate.md`](../core/pre-edit-gate.md) for
  the pre-edit form of this same rule.

## Step 5 — testing / tooling additions

For testing and tooling changes, confirm:

- The new or changed commands work locally with the documented
  setup.
- Docs and PR descriptions accurately describe what the tests
  do and do not prove.
- New validation paths are included in the self-review, not
  delegated entirely to CI.

## Step 6 — multi-commit review

For multi-commit work, also review:

- Whether each commit would make sense to a reviewer on its
  own.
- Whether a later commit silently fixed issues introduced by an
  earlier one.
- Whether any structural change remains undocumented.
